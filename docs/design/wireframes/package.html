What happens next

  • When you press Submit in the portal, the extension logs the application under Applications.
  • Until then the job sits in Saved with "Package ready".
  • Editing any part re-opens that step for approval.
Design notes
  • Over 10 s, so: per-part progress, a time estimate, and finished parts open straight away. The CV usually finishes first and is the step that needs you most, so "Start reviewing" is the next action, not waiting.
  • Leaving the page is safe and said so; the Feed row picks up "Package ready". "Stop" keeps finished parts.
  • Cost is shown per package because there's a hard monthly cap.
Design notes
  • Radio cards, all three visible, recommended one pre-selected with its reason. Each option says what you lose by choosing it (Easy Apply loses the tailored CV and the extension).
  • Usually a one-click step; it's still a step because the choice decides which screening questions and which portal the rest of the package is built for.
  • The posting also sets the language. When a posting is written in Bulgarian, the whole package (CV, cover letter and screening answers) is generated in Bulgarian by default, not English with Bulgarian phrases, and you can switch it per package.
Design notes
  • Concept B inside A: each requirement shows the profile evidence and the exact CV line it became. The two flags sit inline under their requirement, in amber boxes, and are also listed at the top with jump links.
  • Flag options have no pre-selection on purpose: honesty decisions should be conscious. Each option says how it holds up in an interview, and the "led" option asks for the fact that would justify it.
  • Gaps are named, never covered: CISSP is shown as "left out, not claimed"; Kubernetes asks whether you have evidence, and if so it goes into the master profile first, not only this CV.
  • Diff vs master profile is a list of discrete edits with an undo each, so every change is auditable and reversible.
  • Approve is aria-disabled (still focusable, explains itself) rather than disabled; pressing it gives the Blocked state.
Design notes
  • Preview / Changes is a toggle inside the CV step, not a separate step: the review happens in Changes, the preview confirms what that review produced. It shows the wording you chose on each flag.
  • The layout is a fixed, ATS-tested template designed in design step 5 (single column, real text, embedded fonts). The AI only fills content; it never moves blocks, picks fonts or adds columns.
  • One restrained accent: headings and the name in --ink, everything else in body grey. No icons, no skill bars.
  • Photo is off by default and switchable per package ("Standard + photo", suggested for local Bulgarian employers that expect one). The choice is remembered per package, not globally.
  • Language follows the posting (Bulgarian posting → Bulgarian package by default) and can be switched per package here; switching regenerates the CV, letter and screening answers together so they never mix languages.
  • The preview is the exact file that gets uploaded and downloaded, rendered from the same PDF, not an HTML approximation. Fit shows the whole page; 100% scrolls inside the preview, never the page.
  • Warning variant: if content spills onto page 2 the page chip turns amber ("2 pages · 4 lines on page 2") with a banner: "This CV runs onto a second page. Tighten it?" → Shorten the oldest role / Drop the summary's last sentence / Keep 2 pages. Tightening shows as normal edits in Changes, each undoable; it never shrinks the font or margins.
Design notes
  • Pressing Approve with an open flag moves focus to an alert that names the flag, why it matters and links straight to it; the flag gets a strong outline. Resolved flags turn green and stay visible with what you chose.
  • The same rule applies everywhere: editing an approved part later re-opens that step, so the final package can never contain an unresolved flag.
Design notes
  • Editable in place; the word count is always visible against the target. Highlights show which sentences were written for this job versus carried over from your usual letter, so you can check the parts most likely to be wrong.
  • "Regenerate with an instruction" keeps the current draft (drafts are paged), so nothing is lost by trying.
  • Checks tie back to the CV step's decisions: the letter can't say "led" if the CV says "took part", and the gap you chose to name is named.
Design notes
  • Same letterhead as the CV (name and contact line, same type and rule), so the two files read as one set. Date, company address and a "Re:" line with the job ID are filled by the template, not the model.
  • The layout is a fixed, ATS-tested template designed in design step 5 (single column, real text, embedded fonts). The AI only fills content; it never moves blocks, picks fonts or adds columns.
  • One restrained accent: headings and the name in --ink, everything else in body grey. No icons, no skill bars.
  • The preview is the exact file that gets uploaded and downloaded, rendered from the same PDF, not an HTML approximation. Fit shows the whole page; 100% scrolls inside the preview, never the page.
  • Controls are deliberately few: download, back to edit. Wording changes happen in the editor; the "written for Kestrel" highlights never reach the file.
Design notes
  • Questions in the portal's order, each with its origin: Answer bank, adapted (with what changed) or New draft. New company-specific answers are not saved to the bank; reusable ones offer to be.
  • Salary is always "Needs you": the range, your floor and your last answer are shown, plus a suggested number. The field type follows the portal (single number).
  • Word limits come from the portal form and show as a live count, not only on overflow.
Design notes
  • Shows what the parser actually extracted, in reading order, with lost fields marked: more useful than a score. Pass/fail per check, no composite number (see cv-writing-and-evaluation.md §12).
  • The fix asks for the real months instead of guessing them, and offers to update the master profile so it doesn't come back.
  • Missing keywords that are deliberate gaps count as a pass, with the reason.
Design notes
  • Says which part failed, why, and that the rest is saved. One automatic retry already happened; the next one is yours to trigger.
  • Review continues: a failure in one part doesn't block the steps before it.
Design notes
  • A cap is a limit you set, not an error, so it's amber. Raising it is a Settings change you make yourself; the app never raises it.
  • Three ways forward: raise the cap, write the missing part yourself, or wait. The ATS check runs locally and continues regardless.
Design notes
  • One primary action: open the target posting, where the extension takes over. The user presses Submit; the app never does.
  • The summary records your honesty decisions in words, so you can answer for them in an interview.
  • Time since opening the job is shown against the under-10-minutes goal.
